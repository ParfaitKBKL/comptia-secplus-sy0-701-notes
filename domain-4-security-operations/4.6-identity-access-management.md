## Account Lifecycle

```
Identity verification -> Provisioning -> Permission assignment -> Monitoring -> De-provisioning
```

| Step | Description |
|---|---|
| **Identity proofing** | Verify identity before provisioning (ID verification, manager approval) |
| **Provisioning** | Create accounts with appropriate rights - based on role, not individual requests |
| **Monitoring** | Monitor account activity - detect anomalies |
| **Attestation**| Periodic review process to confirm  appropriate acces right!
| **De-provisioning** | **Immediately remove access** when an employee leaves - critical for preventing insider threats |

> **Rapid de-provisioning is crucial.** A terminated employee with active access for weeks represents a major risk. Offboarding procedures must be automated and immediate.

## Federation and SSO

**Federation:** Trust relationship between identity providers - allows users to authenticate once and access resources across multiple organizations.

| Protocol | Description |
|---|---|
| **SAML** (Security Assertion Markup Language) | XML-based; used for enterprise SSO (web applications). Exchanges authentication assertions. |
| **OAuth** | Authorization framework - grants limited access without sharing credentials (e.g., "Sign in with Google") |
| **OpenID Connect (OIDC)** | Authentication layer on top of OAuth - adds identity to authorization |
| **LDAP** | Protocol for querying directory services (Active Directory) - user and group lookups |

### SSO Advantages and Risks

| Advantages | Risks |
|---|---|
| Fewer passwords to manage | Single point of failure - IdP compromise = access to all services |
| Better user experience | MFA on the IdP is therefore critical |
| Centralized access control | Attack on IdP = maximum blast radius |

## Access Control Models

| Model | Description | Example |
|---|---|---|
| **DAC** (Discretionary) | Owner decides permissions | Windows NTFS permissions - user can share their files |
| **MAC** (Mandatory) | OS enforces based on classification labels | Government classified systems - user cannot change labels |
| **RBAC** (Role-based) | Permissions assigned to roles | "Marketing Group" accesses the CRM |
| **Rule-based** | If-then rules applied to everyone | Firewall ACL |
| **ABAC** (Attribute-based) | Decisions based on user/resource attributes | Access if department=Finance AND location=HQ |
| **Time-of-day** | Restrict access to business hours | Contractors can only connect from 8am to 6pm |
| **Least privilege** | Minimum required permissions | No local admin by default |

## Multi-Factor Authentication (MFA)

Requires 2+ factors from:

| Factor | Type | Example |
|---|---|---|
| **Something you know** | Knowledge | Password, PIN, security question |
| **Something you have** | Possession | TOTP token, smart card, hardware key (YubiKey) |
| **Something you are** | Inherence | Fingerprint, retina, face |
| **Somewhere you are** | Location | GPS, corporate network |

> **MFA** requires proof from two or more distinct factor categories

### MFA Implementations

| Type | Description |
|---|---|
| **Biometrics** | FAR (False Acceptance Rate) vs. FRR (False Rejection Rate) - crossover point = EER (Equal Error Rate) |
| **Hard token** | Physical device generating an OTP (RSA SecurID, YubiKey) |
| **Soft token** | App-based OTP (Google Authenticator, Microsoft Authenticator) |
| **Security key** | FIDO2/WebAuthn hardware key - **phishing-resistant** (bound to the domain) |

### TOTP vs. HOTP

| | TOTP | HOTP |
|---|---|---|
| Based on | Time | Counter |
| Validity | 30 seconds | Until used |
| Standard | RFC 6238 | RFC 4226 |

## Password Concepts

Current recommendations (NIST SP 800-63B):

| Practice | NIST Recommendation |
|---|---|
| **Length** | Minimum 8 characters (ideally 12+) - favor passphrases |
| **Forced expiration** | **Do not enforce** at regular intervals - change only if compromised |
| **Complexity** | Do not force arbitrary complex rules (`P@ssw0rd!` is less secure than a long passphrase) |
| **Reuse** | Prohibit reuse - history policy |
| **Password manager** | Recommended - enables unique and complex passwords per site |
| **Passwordless** | FIDO2, biometrics, magic link - the future |

## Privileged Access Management (PAM)

| Feature | Description |
|---|---|
| **Just-in-time permissions** | Elevated access granted on demand, automatically revoked after the session |
| **Password vaulting** | Store and automatically rotate privileged credentials |
| **Ephemeral credentials** | Short-lived credentials generated per session - no persistent service accounts |
| **Session recording** | Record privileged admin sessions for audit and forensics |

> **PAM significantly reduces the blast radius** of credential theft. Even if an attacker steals a vaulted credential, it expires quickly and sessions are recorded.

## Practice Questions

**Q: A user signs into an app using their Google credentials without creating a new account. What protocol is likely used?**
Answer: **OAuth / OpenID Connect (OIDC)** - "Sign in with Google" uses OAuth for authorization and OIDC for identity.

**Q: An attacker obtains a sysadmin's password. The organization uses PAM with ephemeral credentials. How does this limit the risk?**
Answer: PAM credentials **expire after the session** - the stolen password is already stale, and the attacker cannot use it for a subsequent login.

**Q: Which MFA implementation is most resistant to phishing attacks?**
Answer: **FIDO2/WebAuthn** (security key) - cryptographically bound to the site's domain, impossible to use on a fake site.
