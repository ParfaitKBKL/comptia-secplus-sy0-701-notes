## Cloud Architecture

### Shared Responsibility Matrix

| Responsibility | IaaS | PaaS | SaaS |
|---|---|---|---|
| Physical infrastructure | Provider | Provider | Provider |
| Networking | Shared | Provider | Provider |
| Hypervisor/Virtualization | Provider | Provider | Provider |
| Operating System | **Customer** | Provider | Provider |
| Applications | **Customer** | **Customer** | Provider |
| **Data** | **Customer** | **Customer** | **Customer** |
| Identities/Access | **Customer** | **Customer** | **Customer** |

> **Fundamental rule:** The customer is **always** responsible for their **data**, regardless of the deployment model. This is the most commonly tested point on this topic.

### Cloud Deployment Models

| Model | Description | Use Case |
|---|---|---|
| **Public cloud** | Shared resources at a third-party provider (AWS, Azure, GCP) | Scalability, reduced cost |
| **Private cloud** | Dedicated cloud infrastructure for one organization | Regulated industries (healthcare, finance) |
| **Hybrid cloud** | Mix of public + private with interconnection | Flexibility + sensitive data on-prem |
| **Community cloud** | Shared between organizations with similar requirements | Governments, hospitals |

### Hybrid Considerations
- On-premises + Cloud: identity federation, consistent security policies across both
- Data classification determines what can go to the cloud
- **Data sovereignty:** data is subject to the laws of the country where it is physically stored

## Modern Architecture Patterns

| Pattern | Description | Security Consideration |
|---|---|---|
| **IaC** (Infrastructure as Code) | Infrastructure defined in code (Terraform, Ansible, Pulumi) | Version control, secrets management in code, configuration drift |
| **Serverless** | No server management; event-driven functions (Lambda, Azure Functions) | Shared runtime security, function privileges, event injection |
| **Microservices** | App broken into small independent services | Large API attack surface, inter-service auth (mutual TLS) |
| **Containerization** | Isolated app environments (Docker, Kubernetes) | Image scanning, pod security policies, secrets management, namespace isolation |
| **Virtualization** | Multiple VMs on one host | VM escape risk, hypervisor patching |
| **SDN** (Software-Defined Networking) | Network controlled by a software layer | Control plane attack surface |

## Network Infrastructure

| Concept | Description |
|---|---|
| **Air-gapped** | Physically isolated from all other networks - maximum security (SCADA, military systems) |
| **Physical isolation** | Separate hardware, not just logical separation |
| **Logical segmentation** | VLANs, firewall zones - logical separation on shared infrastructure |
| **On-premises** | Customer controls all layers - maximum responsibility |
| **Centralized vs. decentralized** | Centralized = single point of control (and single point of failure); decentralized = resilient but complex |

---

## Specialized Systems

| System | Security Challenge |
|---|---|
| **IoT** | Limited patching capability, default credentials, large attack surface, proprietary protocols |
| **ICS/SCADA** | Operational technology - patching disrupts operations, very long lifecycles (10-20+ years) |
| **RTOS** (Real-time OS) | Hard real-time constraints - security features are often stripped |
| **Embedded systems** | Often no OS update path, hardcoded firmware |
| **High availability** | Redundant design prevents availability attacks, but complexity introduces new risks |

## Architecture Considerations (Trade-offs)

| Consideration | Key Question |
|---|---|
| **Availability** | What is the uptime requirement? Any single points of failure (SPOF)? |
| **Resilience** | Can it recover from partial failure? RTO/RPO achievable? |
| **Cost** | Security controls vs. budget - justify by ALE (risk quantification) |
| **Responsiveness** | Latency impact of security controls (SSL inspection, proxy) |
| **Scalability** | Can security scale with the environment? |
| **Ease of deployment** | Complex security leads to configuration errors and vulnerabilities |
| **Risk transference** | Can risk be offloaded to cloud provider? Cyber insurance? |
| **Ease of recovery** | RTO/RPO targets met? |
| **Patch availability** | Can patches be applied? How often? |
| **Inability to patch** | Compensating controls needed (isolation, monitoring, WAF) |

## Practice Questions

**Q: A company migrates to AWS and wonders who is responsible for securing data stored in S3. Who is responsible?**
Answer: **The customer** - data is always the customer's responsibility in the shared responsibility model.

**Q: An organization deploys a SCADA system to control its factory. Why is it difficult to patch regularly?**
Answer: Patching **disrupts operations** (real-time critical system) and OT system lifecycles are very long. Mitigation goes through **network isolation** (air gap or dedicated VLAN).

**Q: Which cloud deployment model lets an organization keep sensitive data on-premises while using public cloud resources for other workloads?**
Answer: **Hybrid cloud**.
