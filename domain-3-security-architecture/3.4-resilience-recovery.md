## High Availability

### Load Balancing vs. Clustering

| | Load Balancing | Clustering |
|---|---|---|
| Purpose | Distribute traffic | Failover + performance |
| Nodes | Independent | Share state |
| Failure handling | Remove failed node | Active/passive or active/active |
| Example | Multiple web servers behind a LB | Database cluster |

### Clustering Modes

| Mode | Description | Availability |
|---|---|---|
| **Active/Active** | All nodes process requests simultaneously | Very high - maximum capacity |
| **Active/Passive** | One active node, others on standby ready to take over | High - failover in seconds/minutes |

---

## Recovery Site Considerations

| Site Type | Recovery Time | Cost | Data State |
|---|---|---|---|
| **Hot site** | Minutes | High | Real-time sync - mirror |
| **Warm site** | Hours to days | Medium | Near real-time - requires partial restoration |
| **Cold site** | Days to weeks | Low | Requires full restoration from backups |

- **Geographic dispersion:** Sites in different regions to protect against regional disasters
- **Cloud as hot site:** Increasingly, cloud serves as the hot site (DR-as-a-Service)

---

## Business Continuity Metrics

| Metric | Definition | Example |
|---|---|---|
| **RTO** (Recovery Time Objective) | Maximum acceptable downtime duration | "We must be back online within 4 hours" |
| **RPO** (Recovery Point Objective) | Maximum acceptable data loss | "We cannot lose more than 1 hour of data" |
| **MTTR** (Mean Time to Repair) | Average time to resolve a failure | IT team responsiveness metric |
| **MTBF** (Mean Time Between Failures) | Average time between two failures | System reliability indicator |

> **RTO vs RPO:**
> - RTO = *time* (how long can we stay offline?)
> - RPO = *data* (how much data can we lose?)
> An RPO of 1 hour requires backups at least every hour.

## Capacity Planning

Three dimensions:
- **People:** Sufficient trained staff for operations and incident response
- **Technology:** Hardware/software capacity for peak load plus resilience
- **Infrastructure:** Network bandwidth, power supply, cooling

## Resilience Testing

| Test | Description | Disruption |
|---|---|---|
| **Tabletop exercise** | Scenario-based discussion - no systems affected | None |
| **Simulation** | Realistic exercise - teams execute response procedures | Minimal |
| **Failover** | Actually switches to backup systems | Possible service impact |
| **Parallel processing** | Both primary and backup run simultaneously | None - most thorough |

## Backup Strategies

| Type | What is backed up | Restoration complexity |
|---|---|---|
| **Full** | Everything | Simple (single restore) |
| **Incremental** | Changes since the last backup (of any type) | Complex (full + all incrementals since) |
| **Differential** | Changes since the last **full** backup | Medium (full + last differential) |

### Practical Comparison

```
Monday    : Full backup
Tuesday   : Incremental (changes since Monday)
Wednesday : Incremental (changes since Tuesday)
Thursday  : Incremental (changes since Wednesday)

To restore Thursday: Full (Monday) + Tuesday + Wednesday + Thursday = 4 operations

---

With Differential:
Monday    : Full backup
Tuesday   : Differential (changes since Monday full)
Wednesday : Differential (ALL changes since Monday full)
Thursday  : Differential (ALL changes since Monday full)

To restore Thursday: Full (Monday) + Differential (Thursday) = 2 operations
```

### Backup Considerations

| Aspect | Detail |
|---|---|
| **Onsite** | Fast restoration, vulnerable to the same physical disaster |
| **Offsite** | Slower restoration, protected against on-site events |
| **3-2-1 Rule** | 3 copies, 2 different media types, 1 offsite |
| **Frequency** | Based on RPO - a 1-hour RPO requires near-continuous backups |
| **Encryption** | Backup tapes/files must be encrypted |
| **Snapshots** | Point-in-time copy - fast and space-efficient (not a substitute for backup) |
| **Replication** | Real-time or near-real-time copy to another site |
| **Journaling** | Log-based recovery - records all transactions for point-in-time restoration |

> **Snapshots are not backups** - they often depend on the same storage system. If the disk fails, the snapshot is also lost.

## Power Resilience

| Equipment | Role |
|---|---|
| **UPS** (Uninterruptible Power Supply) | Immediate emergency battery - keeps systems running during brief outages, allows clean shutdown |
| **Generator** | Long-duration power during extended outages |

> The UPS provides transition power while the generator starts (typically 10-30 seconds). Without a UPS, systems fail during that gap.

## Practice Questions

**Q: An organization has an RPO of 2 hours. What is the minimum backup frequency required to meet this RPO?**
Answer: **Every 2 hours** (or more frequently) - the RPO defines the maximum acceptable data loss.

**Q: An organization must restore its systems as quickly as possible after a disaster and can afford a high cost. What type of recovery site should they use?**
Answer: **Hot site** - systems already configured, data synchronized in real time, recovery in minutes.

**Q: A company performs a full backup on Sunday and differential backups Monday through Saturday. If a failure occurs on Friday, how many backup items need to be restored?**
Answer: **2** - the full backup from Sunday plus the differential backup from Friday (which contains all changes since Sunday).
