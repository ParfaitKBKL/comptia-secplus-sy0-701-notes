## Public Key Infrastructure (PKI)

PKI manages digital certificates and public/private key pairs.

| Component | Role |
|---|---|
| **Public key** | Shared openly; used to encrypt or verify signatures |
| **Private key** | Secret; used to decrypt or create signatures - never leaves the owner |
| **Key escrow** | Private key copy stored by a trusted third party (e.g., for legal access or recovery) |
| **Certificate Authority (CA)** | Issues and signs digital certificates - root of trust |
| **Root of trust** | The CA at the top of the chain - implicitly trusted by OS and browsers |
| **Certificate Signing Request (CSR)** | Request sent to CA to get a certificate signed |
| **CRL (Certificate Revocation List)** | List of revoked certificates - checked periodically |
| **OCSP (Online Certificate Status Protocol)** | Real-time check if a specific certificate is still valid - more efficient than CRL |
| **Wildcard certificate** | `*.example.com` - covers all subdomains at one level |

### Self-Signed vs. Third-Party

| | Self-Signed | Third-Party (Public CA) |
|---|---|---|
| Signed by | The same entity that issued it | DigiCert, Let's Encrypt, Comodo, etc. |
| Browser trust | No - security warning shown | Yes - trusted by default |
| Use case | Internal infrastructure, testing | Public websites, online services |

### Chain of Trust

```
Root CA (self-signed, highly protected, often offline)
    |
Intermediate CA (signs end-entity certificates)
        |
End-entity certificate (server, user)
```

## Encryption

### Symmetric vs. Asymmetric

| | Symmetric | Asymmetric |
|---|---|---|
| Keys | Same key to encrypt and decrypt | Public key encrypts, private key decrypts |
| Speed | Fast | Slow (complex math) |
| Key exchange problem | Yes - how to share the key securely? | No - public key is safe to share |
| Use case | Bulk data encryption | Key exchange, digital signatures |
| Algorithms | **AES**, DES (obsolete), 3DES (obsolete) | **RSA**, **ECC**, Diffie-Hellman |

> **Hybrid encryption:** Asymmetric is used to securely exchange a symmetric key, then symmetric is used for the actual data. This is exactly how **TLS** works.

### Encryption Levels

| Level | Tool | Protects against |
|---|---|---|
| **Full Disk (FDE)** | BitLocker (Windows), FileVault (macOS), LUKS (Linux) | Physical theft of the disk/device |
| **Partition** | BitLocker To Go, VeraCrypt | Compromise of a specific partition |
| **File** | EFS, GPG, 7-Zip AES | Unauthorized access to individual files |
| **Volume** | VeraCrypt | Logical encrypted volume |
| **Database** | Transparent Data Encryption (TDE) | Direct access to DB files |
| **Record** | Field/row-level encryption | Internal DB access with insufficient rights |

### Key Exchange - Diffie-Hellman (DH)

Allows two parties to establish a shared secret over an insecure channel **without ever transmitting the key**.

| Variant | Key feature |
|---|---|
| **DHE** (Ephemeral) | New key per session - supports **Perfect Forward Secrecy (PFS)** |
| **ECDHE** | Elliptic curve variant - smaller keys, faster |

> **Perfect Forward Secrecy:** If the server's private key is compromised later, past sessions remain encrypted because each session had its own ephemeral key.

## Hashing

One-way function: input > fixed-length digest. Not reversible.

| Algorithm | Output Size | Status |
|---|---|---|
| MD5 | 128-bit | **Broken** - known collision attacks, do not use for security |
| SHA-1 | 160-bit | **Deprecated** - known weaknesses |
| SHA-256 | 256-bit | **Recommended** - current standard |
| SHA-3 | Variable | Current NIST standard, quantum-resistant |
| BLAKE2 | Variable | Fast, used in modern tools |

### Salting

Adding a unique random value (the salt) to a password **before** hashing it.

- Prevents rainbow table attacks
- Each user gets a unique salt - two users with the same password get different hashes
- The salt is stored in plaintext alongside the hash - not a secret, just a randomizer

### Key Stretching

Apply a hash function many times (iterations) to slow down brute force attacks:
- **PBKDF2** - standard, used in WPA2
- **bcrypt** - adaptive, adjustable cost factor
- **scrypt** - resistant to GPU/ASIC attacks

## Digital Signatures

Provide **integrity + non-repudiation**.

**Full process:**
1. Sender hashes the message
2. Sender encrypts the hash with their **private key** - this is the signature
3. Receiver decrypts the signature with the sender's **public key** - gets the hash
4. Receiver hashes the received message and compares - if they match, integrity is confirmed

> **Golden rule:** Sign with the **private key** (proves identity). Verify with the **public key**.

## Obfuscation Techniques

| Technique | Description | Key difference |
|---|---|---|
| **Steganography** | Hiding data inside another file (image, audio, video) | Data is *hidden*, not encrypted |
| **Tokenization** | Replace sensitive data with a non-sensitive token (CC number > token ID) | Token replaces the real value, stored separately in a vault |
| **Data masking** | Partially obscure data | Display `****-****-****-1234` - real value still exists |
| **Obfuscation** | Make code/data harder to understand | Source code obfuscation, renamed variables |

### Tokenization vs. Encryption

| | Tokenization | Encryption |
|---|---|---|
| Reversible | Via the token vault | Via the encryption key |
| Original data stored | Separately in a secure vault | No - transformed to ciphertext |
| Key required | No | Yes |
| PCI DSS use | Yes - store token, not the CC number | Yes |

## Hardware Security Tools

| Tool | Purpose |
|---|---|
| **TPM** (Trusted Platform Module) | Chip on the motherboard - stores keys, enables measured boot, disk encryption (BitLocker) |
| **HSM** (Hardware Security Module) | Dedicated hardware for key management - FIPS 140-2/3 validated, used in production PKI |
| **Key Management System (KMS)** | Software platform to manage the key lifecycle |
| **Secure Enclave** | Isolated CPU area for sensitive operations (Apple T2/M1, ARM TrustZone) |

## Blockchain

Distributed ledger - each block contains the hash of the previous block.

- **Immutability:** Altering a block invalidates all subsequent blocks
- **Open public ledger:** Transparent, anyone can verify
- Security use cases: Audit logs, certificate transparency logs

## Practice Questions

**Q: An organization stores credit card numbers in its database by replacing them with random identifiers. The real values are stored in a separate secure system. What mechanism is being used?**
Answer: **Tokenization** - the token replaces the real value, which is stored in a separate vault.

**Q: Which cryptographic property ensures that the sender of a message cannot deny having sent it?**
Answer: **Non-repudiation** - guaranteed by digital signatures (private key = unique identity).

**Q: Which hashing algorithm is currently recommended for password storage in production?**
Answer: **bcrypt or PBKDF2** (with salting and high iteration counts) - SHA-256 alone without salting/stretching is insufficient for passwords.

**Q: Which TLS feature provides Perfect Forward Secrecy?**
Answer: **ECDHE (Ephemeral Diffie-Hellman)** - new session key per connection.
