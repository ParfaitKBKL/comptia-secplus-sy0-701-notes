# 1.3 - Change Management and Security Impact

**Official CompTIA SY0-701 objective:** 1.3 - Explain the importance of change management processes and the impact to security.
**Recommended resource:** Professor Messer SY0-701 - "Change Management" (Domain 1, Section 1.3)

---

## Why Change Management Matters for Security

Uncontrolled changes are a leading cause of outages and security incidents. Change management ensures changes are planned, tested, approved, and reversible.

**Core principle:** Without a change process, an emergency patch can introduce a regression, expose an unintended port, or break a critical dependency.

---

## Business Processes Impacting Security Operations

| Process | Security Relevance |
|---|---|
| **Approval process** | Prevents unauthorized changes; requires formal sign-off before any action |
| **Ownership** | Clear accountability - each asset has a named owner responsible for its security |
| **Stakeholders** | Identify who is impacted before making changes |
| **Impact analysis** | Assess what could break (CIA triad implications: availability, integrity, confidentiality) |
| **Test results** | Validate in a staging/pre-production environment first |
| **Backout plan** | Mandatory rollback procedure if the change fails - **required before any approved change** |
| **Maintenance window** | Scheduled downtime - minimizes risk to production |
| **Standard Operating Procedure (SOP)** | Documented steps - reduces human error |

> **Key exam concept:** A **backout plan** is required before any approved change. "We'll figure it out if it breaks" is not an acceptable answer.

---

## Technical Implications of Changes

| Implication | Concrete example |
|---|---|
| **Allow lists / Deny lists** | Changing firewall rules can block legitimate traffic or allow unintended traffic |
| **Restricted activities** | Some changes require elevated privileges or specific roles |
| **Downtime** | Patching a critical server may require service interruption |
| **Service restart** | Many configuration changes require daemon restarts |
| **Application restart** | Web app configs often need a restart to take effect |
| **Legacy applications** | Do not support modern configurations; change risk is higher - compensating controls needed |
| **Dependencies** | Updating one component can break dependent services (e.g., library update) |

---

## Documentation Requirements

Every change must be documented:

- **Update diagrams:** Network topology, data flows must reflect the new state
- **Update policies/procedures:** If the change alters how a process works
- **Version control:** All configuration files and scripts should be versioned

> Undocumented changes create a "security debt" - you cannot protect what you do not know exists.

---

## Version Control

Git (or equivalent) for:
- Configuration files (Ansible playbooks, Terraform, GPO exports)
- Scripts and automation
- Security policies and runbooks

**Benefits:** Full audit trail, rollback capability, peer review via pull requests, configuration drift detection.

---

## Change Management Flow (Simplified)

```
Change request
    |
Impact analysis (CIA triad, dependencies)
    |
Stakeholder review
    |
Approval (CAB - Change Advisory Board)
    |
Testing in staging environment
    |
Schedule maintenance window
    |
Implementation
    |
Validation (did the change work?)
    |
Documentation and closure
    |
[If failure: execute Backout Plan]
```

---

## Key Roles

| Role | Responsibility |
|---|---|
| **Change Owner** | Requests and owns the change |
| **CAB (Change Advisory Board)** | Reviews and approves significant changes |
| **Emergency CAB** | Approves urgent changes outside the normal cycle |
| **Change Manager** | Coordinates the overall process |

---

## Practice Questions

**Q: A sysadmin applies a critical patch without following the change process. What is most likely missing?**
Answer: **Backout plan and CAB approval** - both are required even for urgent patches (Emergency CAB).

**Q: After a configuration update, several dependent services go down. Which Change Management step would have prevented this?**
Answer: **Impact analysis** - identify dependencies before making the change.

**Q: Why are undocumented changes a security risk?**
Answer: Cannot audit, cannot roll back, cannot know the actual state of the system - creates an unknown attack surface.
