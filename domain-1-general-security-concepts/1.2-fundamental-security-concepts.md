## The CIA Triad

The foundation of all security decisions. Every control, technology, and policy serves to protect one of these three pillars.

| Pillar | Definition | Attack that breaks it | Control example |
|---|---|---|---|
| **Confidentiality** | Data is accessible only to authorized parties | Data breach, eavesdropping, shoulder surfing | Encryption, MFA, ACL, physical access control |
| **Integrity** | Data is accurate and unmodified | Man-in-the-Middle, SQL injection, file tampering | Hashing, digital signatures, input validation, HMAC |
| **Availability** | Systems are accessible when needed | DDoS, ransomware, hardware failure | Redundancy, backups, load balancing, UPS, failover sites |

> Some frameworks add **Non-repudiation**: the ability to prove an action occurred and prevent its denial. Achieved via digital signatures and audit logs.

### Memory Aid
- **C**onfidentiality: **C**ryption (encryption)
- **I**ntegrity: Hash**i**ng
- **A**vailability: **A**rchitecture (redundant)

## AAA Framework

**Authentication > Authorization > Accounting**

### Authentication - Prove who you are

| Factor | Type | Examples |
|---|---|---|
| **Something you know** | Knowledge | Password, PIN, security question |
| **Something you have** | Possession | TOTP token, smart card, hardware key (YubiKey) |
| **Something you are** | Inherence | Fingerprint, retina, face recognition |
| **Somewhere you are** | Location | GPS location, corporate network |

- Authenticating *people*: MFA, passwords, biometrics
- Authenticating *systems*: Certificates, API keys, device certificates (802.1X)

### Authorization - Define what you can do

| Model | Description | Example |
|---|---|---|
| **RBAC** (Role-Based) | Permissions linked to roles | "Marketing group" accesses CRM |
| **ABAC** (Attribute-Based) | Decisions based on attributes | Access if department=Finance AND location=HQ |
| **MAC** (Mandatory) | OS enforces based on classification labels | Government classified systems |
| **DAC** (Discretionary) | Owner decides | Windows NTFS permissions |
| **Rule-based** | If-then rules applied to all | Firewall ACL |

### Accounting - Record what you did

- SIEM logs, audit trails, access logging
- Enables non-repudiation and forensic investigations

## Zero Trust

**"Never trust, always verify"** - Assume breach by default.

ZT replaces the traditional castle-and-moat model where everything inside the network is implicitly trusted.

### Control Plane (policy decisions)

| Component | Role |
|---|---|
| **Policy Engine** | Decides grant/deny based on rules and risk level |
| **Policy Administrator** | Communicates decisions to enforcement points |
| **Adaptive Identity** | Dynamic risk evaluation per request (device health, location, time) |
| **Threat Scope Reduction** | Minimize blast radius - micro-segmentation, least privilege |
| **Policy-driven Access Control** | Access decisions based on evaluated context, not network location |

### Data Plane (enforcement)

| Component | Role |
|---|---|
| **Subject/System** | The entity requesting access (user, device, workload) |
| **Policy Enforcement Point (PEP)** | Where access is granted or denied (proxy, gateway) |
| **Implicit Trust Zones** | Legacy concept ZT replaces - never trust anything inside the perimeter |

> A VPN alone is not Zero Trust. ZT = identity + device health + context, evaluated at every access request.

## Gap Analysis

Process of comparing current security posture against a desired baseline or framework (NIST CSF, ISO 27001, CIS Controls).

**Steps:**
1. Define the target state (which framework/baseline?)
2. Assess the current state (audit, interviews, scans)
3. Identify gaps
4. Prioritize remediation (impact x effort)

## Physical Security

### Barriers and Access Control

| Control | Type | Notes |
|---|---|---|
| **Bollards** | Physical + Preventive | Block vehicle ramming attacks |
| **Access control vestibule (Mantrap)** | Physical + Preventive | Airlock - prevents tailgating, only one person at a time |
| **Fencing** | Physical + Preventive + Deterrent | Perimeter control, visual deterrent |
| **Security guard** | Multiple | Deterrent + Preventive + Detective |
| **Access badge** | Technical + Detective | Logs entries, proves presence |
| **Lighting** | Physical + Deterrent | Reduces cover for attackers, improves visibility |
| **Faraday cage** | Physical + Technical | Blocks electromagnetic signals - protects against RF interception |

### Sensors

| Sensor | How it works |
|---|---|
| **Infrared** | Detects heat signatures (body heat) |
| **Pressure** | Floor sensors, detects weight/movement |
| **Microwave** | Detects motion through walls |
| **Ultrasonic** | Sound-based motion detection |

## Deception and Disruption Technology

Used to detect attackers, waste their time, and gather threat intelligence.

| Tool | Purpose | Concrete example |
|---|---|---|
| **Honeypot** | Fake single system to lure attackers | SSH server exposed on internet with fake files |
| **Honeynet** | Fake network of systems - more realistic, more intel | Complete fake corporate infrastructure |
| **Honeyfile** | Fake file triggering an alert when accessed | `passwords.txt`, `credit_cards.xlsx` on a server |
| **Honeytoken** | Fake credential or data element - detects misuse | Fake Active Directory account that should never log in, fake API key |

> **Exam tip:** Honeytokens are often embedded in real systems. A fake account in AD that should never log in immediately triggers an alert if used.

## Practice Questions

**Q: An admin places fake entries in the customer database to detect if someone exfiltrates data. What mechanism is being used?**
Answer: **Honeytoken** - fake data embedded in real systems to detect unauthorized access.

**Q: A user authenticates with a password then receives a code on their phone. What framework is being applied?**
Answer: **AAA with MFA** - Authentication with two factors (something you know + something you have).

**Q: Which Zero Trust component makes the final decision to allow or deny access?**
Answer: **Policy Engine**.
